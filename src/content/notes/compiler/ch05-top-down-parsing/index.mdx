## Parse Table

### LL(k) and Predict Function

我們首先定義一個 Prediction Function

$$
\mathrm{Predict}(A \to X_1 \ldots X_m) = \begin{cases}
(\mathrm{First}(X_1\ldots X_m) \setminus \{\lambda\}) \cup \mathrm{Follow}(A) &\text{if }\lambda \in \mathrm{Follow}(A) \\
\mathrm{Follow}(A) &\text{otherwise}
\end{cases}
$$

如果我們需要找到一個 $LL(1)$ 的 parsing method 有一個先決條件就是，對於**同一個 Symbol 的所有 rule 的 Predict set** 一定要是 **disjoint** 的

以此類推我們可以知道想找到 $LL(k)$ 我們就需要 $\mathrm{Predict}_k()$ function，$k$ 就是我們的 First set, Follow set 要往後看幾個 token

### LL(1) Parse Table

我們現在來看看 parse table，首先我們討論一下定義

$$
T: V_n \times V_t \to P \cup \{\text{Error}\}
$$

- $T[A][t] = A \to X_1\ldots X_m$ if $t \in \mathrm{Prediction}(A \to X_1\ldots X_m)$
- $T[A][t] = \mathrm{Error}$ otherwise


如果發現不是 disjoint 的話，我們填表就會發現某個 entry 裡面有不止一個 rule 可以被放進來，如過是 disjoint 的話，那他就是 $LL(1)$


### Trade-off in Parse Table Implementation

Similar to Scanner，Parser 也有兩種 Implementation：

1. **Built-in (Hardwired Parser)**
   - 將 $LL(1)$ Parsing Table 中的 parsing decisions 直接 **hardwire** 到程式碼中
   - 例如 **Recursive Descent Parser**，透過不同的 procedures 和條件判斷來決定使用哪個 production
2. **Table-driven Parser**
   - 將 parsing decisions 儲存在 **Parsing Table** 中
   - Parser 根據目前的 **Stack Top** 和 **Lookahead Token** 查表，決定下一步使用哪個 production

> **Hardwire** 意思是寫死在程式裡

## Parsing Driver

### Built-in Driver

這是一個基礎的 **Built-in Parsing Driver** 的一部分，每個不同的 production finding 都有被定義在 code 裡面，我們用這個東西來決定 procedure

```txt
procedure A(ts)
    lookahead ← ts.PEEK()
    if lookahead ∈ Predict(p_1) then
        /* Parse using production p_1. */
    else if lookahead ∈ Predict(p_2) then
        /* Parse using production p_2. */
    ...
    else if lookahead ∈ Predict(p_n) then
        /* Parse using production p_n. */
    else
        /* Report a syntax error. */
    end if
end procedure
```

以上是 pseudo code，實際寫出來會像[**這樣**](https://vinsong.csie.org/notes/compiler/ch02-simple-compiler#recursive-descent-parsing)

### Table-Driven Driver

在 $LL(1)$ 的 language 中，我們可以用讓 driver 跟 table 協作，這樣寫出來的 code
- **Smaller Code Size**
    - Recursive Descent Parser 通常每個 Nonterminal 都需要一個 Procedure
    - Table-driven Parser 只需要一個通用的 Driver Program + Parsing Table，可能減少重複的程式碼
- **Faster Execution**
    - Recursive Descent Parser 需要頻繁進行 Function Calls / Returns，產生 Call Stack Overhead
    - Table-driven Parser 使用 Explicit Stack，不需要透過遞迴呼叫來處理 Nonterminals，因此在某些實作中可能更快
- **Portability**
    - Table method 很好做 extension

```txt
procedure LL_PARSER(ts)
    call PUSH(S)
    accepted ← false
    while not accepted do
        if TOS() ∈ Σ then
            call MATCH(ts, TOS())
            if TOS() = $ then
                accepted ← true
            call POP()
        else
            p ← LLtable[TOS(), ts.PEEK()]
            if p = 0 then
                call ERROR("Syntax error — no production applicable")
            else
                call APPLY(p)
end procedure
```

```txt
procedure APPLY(p: A → X_1 ... X_m)
    call POP()
    for i = m downto 1 do
        call PUSH(X_i)
end procedure
```

## Action Symbol of LL(1)

### LL(1) Action Symbols

**Action Symbols** 可以加入 Productions 中，讓 Parser 在 Parsing 過程中執行對應的 **Semantic Actions**，例如 Code Generation

> 後面會提到 Semantic Actions 是啥，以下是一些例子
> 1. **Symbol Table Management**：把變數加入 Symbol Table，記錄名稱、型別等資訊
> 2. **Type Checking**：檢查型別是否相容，例如 int + string 是否合法
> 3. **Intermediate Code Generation**：產生 Intermediate Representation (IR)
> 4. **AST Construction**：建立 Abstract Syntax Tree
> 5. **Semantic Error Reporting**：回報未宣告變數、型別不相容等錯誤

- 遇到 Action Symbol 時，會呼叫對應的 Semantic Routine
- Semantic Routine 不一定需要 Explicit Parameters，所需資料可以透過 **Semantic Stack** 傳遞
- **Semantic Stack** 儲存 Semantic Records，與 **Parse Stack** 不同。
- 在 Table-driven Parser 中，Action Symbols 會被 Push 到 Parse Stack，當它成為 Stack Top 時就執行對應的 Semantic Action。
- Action Symbols 不消耗 Input Tokens

比如說
```c
match(ID);
match(ASSIGN);
exp();
gen_assign();
match(semicolon);
```

## Making Grammar LL(1)

當我們發現一個 Parse table 裡面有兩個 rule (production) 的話

<Fig src="/images/compiler/ch05-top-down-parsing/non-ll1-grammar.webp" caption="Non-LL(1) grammar" width={80} />

橘色部分，兩個 rule 同時存在在同一個 entry 裡面，這種情況叫做 **conflict**，造成的原因有很多，根據原因可以用對應的改寫技巧可以讓他變成 $LL(1)$

### Common prefix

當我們發現有兩個 rule 有共同的 prefix 的時候

$$
\begin{align}
\texttt{<stmt>} &\to \texttt{if <exp> then <stmt>} \\
\texttt{<stmt>} &\to \texttt{if <exp> then <stmt> else <stmt>}
\end{align}
$$

用 **left factoring** 就可以改寫了

$$
\begin{align}
\texttt{<stmt>} &\to \texttt{if <exp> then <stmt> T} \\
\texttt{T} &\to \lambda \mid \texttt{else <stmt>}
\end{align}
$$

### Other Case

還有一些 Case 不行，比如說 **left recursion**，他會造成 stack 的無窮 push

$$
A \to Aa\ |\ b
$$

我們一樣做 left recursion removal

$$
A → b R,\quad
R → a R\ |\ \lambda
$$

<Aside type="tip" title="Example">

$$
\begin{aligned}
1.\quad &\texttt{<stmt>} \to \texttt{<label> <unlabeled stmt>} \\[4pt]
2.\quad &\texttt{<label>} \to \texttt{ID :}
\qquad \mathrm{PredictSet}=\{\texttt{ID}\} \\[4pt]
3.\quad &\texttt{<label>} \to \lambda
\qquad \mathrm{PredictSet}=\mathrm{FOLLOW}(\texttt{<label>}) \\[4pt]
4.\quad &\texttt{<unlabeled stmt>} \to \texttt{ID := <exp> ;}
\end{aligned}
$$

</Aside>
